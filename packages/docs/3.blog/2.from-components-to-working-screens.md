# From components to working screens

> Responsive previews, a consistent source browser, and three example blocks — a first step toward showing how the pieces work together.

PropShow Kit gives you components you can copy into your own project. This update brings more of the surrounding experience into view: how those components fit into a screen, how that screen behaves at different widths, and which files you need to make it your own.

The first examples cover a project overview, a team directory, and workspace settings. Each comes with an interactive preview, source code, documentation, and a registry entry.

## Try the layout at different widths

Block previews now have their own viewport. Drag the right edge, use the keyboard, or choose a PC, iPad, or Phone preset to see the layout respond. The preview uses an iframe, so CSS media queries follow its width.

Presets fit within the available space in the documentation column. Fullscreen gives a larger screen more room, and Reset returns to the default preview.

Longer content scrolls inside the preview. Scrolling at its boundary stays within that viewport, and the resize handle leaves the scrollbar accessible. Dialogs also stay inside the example, so you can inspect their desktop and mobile layouts in context.

Switching between Preview and Code preserves the example's interactive state. You can edit a form, inspect the source, and return to the same draft.

## One source browser for every block

The Code tab now always shows a file tree in the sidebar and the selected source on the right. A single-file example uses the same layout as a block with several files.

For a larger example, that tree also explains the structure. In the team directory, the member list and invitation dialog have separate files: the list owns the records and search, while the dialog owns its draft and open state. You can inspect both, switch files, and copy the code you need.

The installation flow stays familiar. Blocks are registry entries, and the `shadcn-vue` CLI copies their files and dependencies into your project. You continue to own the source.

## Three places to start

- **[Project Overview](/blocks/project-overview)** combines metric cards and deployment status. Switch the reporting period, then narrow the preview to see the cards stack.
- **[Team Members](/blocks/team-members)** adds search, an empty state, member status, and an invitation dialog with duplicate-email validation. Its Code tab shows the complete file structure.
- **[Workspace Settings](/blocks/workspace-settings)** demonstrates an editable form, notification preferences, unsaved-change feedback, and save and discard behavior.

These blocks reuse components already in the kit, including Frame, Status Badge, and Layer Dialog, alongside shadcn-vue primitives. Their documentation explains how the state is owned and where application-specific behavior can be connected.

The examples keep data in memory. Invitations do not send email, and saved settings return to their sample values on refresh. They are starting points for your application's own requests and persistence.

## Where we want to go next

We want to make it easier to move from a useful component to a coherent product screen. That means adding examples around everyday workflows: navigation, editing, permissions, and managing content. Each example should make the connections between components easier to understand and change.

A useful block also needs to show what happens beyond the first successful interaction. Future examples should give loading, empty, error, and retry states the same attention as the initial layout, with clear places to connect real data.

Preview quality will remain part of that work. Keyboard interaction, narrow layouts, dark mode, scrolling, and dialog cleanup all affect whether an example is useful to someone evaluating it. Broader browser checks and examples that exercise those boundaries are part of the direction we want to pursue.

These are directions for the next iterations, rather than features included in this update or a dated release schedule. The goal is to grow a collection that helps you understand a screen, copy a useful starting point, and adapt it without giving up ownership of the code.
