# Common pitfalls

> Most failed installs are a missing shadcn-vue setup, a `@propshow` name used before it is registered, or sample block content left in place.

## Installing it like a package

`npm install prop-show-kit` does nothing useful. There is no package. The CLI command copies source from the registry:

```bash
npx shadcn-vue@latest add https://kit.prop.show/r/frame.json
```

The name form works only after the alias exists in `components.json`. Until then, `@propshow/frame` is an unknown registry, not a shorter URL. The setup is in [The @propshow registry](/guide/registry).

## Skipping shadcn-vue init

These entries import `cn` from `@/lib/utils` and build on official primitives. If Tailwind is not configured, `components.json` is missing, or `cn` lives somewhere else, the copied files will not compile. Run `npx shadcn-vue@latest init` first, then come back to the [Quick Start](/guide).

A project that already uses shadcn-vue does not need a second init. Point the alias at `https://kit.prop.show/r/{name}.json` and add the entry you want.

## Expecting a replacement UI kit

PropShow Kit will not satisfy an install of `button`, `input`, or `dialog`. Those names belong to shadcn-vue. Removing the official components and hoping this registry fills the hole leaves the blocks without the primitives they render. The boundary is spelled out in [Boundaries with shadcn-vue](/guide/boundaries).

## Installing a block and shipping the demo

Blocks are copied with their demonstration content still in the files.

- Hero, logo cloud, and several marketing blocks load sample images from `storage.efferd.com`. Replace those URLs with assets you control before you publish.
- Testimonials ship fictional quotes. They are not endorsements.
- Header blocks share `components/header/navigation.ts`. The links in that file point at `/` until you edit them. Installing a second header reuses the same navigation module, so one edit updates every installed header. Account links (`signInHref`, `signUpHref`) also need real routes.
- Workspace screens (the 工作台 set) keep data in memory. The invitation dialog does not send email. Settings snap back to the sample values on refresh. The preview is there so you can see the states; the request belongs in your app.

Each block page notes what is sample data. Read that section before the screen goes to production.

## Re-adding an entry you have edited

The source in your repository is the source of truth. Running `shadcn-vue add` again for the same name asks to overwrite those files. There is no merge from an upstream package version. If you want the current registry copy, let the CLI overwrite and re-apply your edits from git. If you want to keep your edits, skip the add.

## Dependencies you did not type

A block install is allowed to pull other entries. The spotlight hero brings its header and logo cloud. Workspace screens bring Frame when they use it. Official names in the log (`button`, `tooltip`, `badge`) are shadcn-vue primitives, not extra PropShow components. You do not add those URLs yourself unless you want the primitive on its own.

You can still install Frame, Pricing, or Filters without any block. A component install does not drag in a hero.

## Reading the docs preview as your layout width

Block previews render in an iframe so media queries follow the preview width. Dragging that frame, or picking the phone preset, is how a block behaves at that width. It does not change the docs site around it. In your application the block is normal page content in the scrolling container you give it. Sticky headers need that scrolling ancestor; mounting one inside a nested `overflow: hidden` pane will not stick.

## Dark mode looks unset

Components use semantic tokens (`background`, `foreground`, `border`, `muted`). If dark mode never switches, the project is missing the shadcn-vue theme variables, not a PropShow color pack. Fix the theme on the shadcn-vue side and both libraries follow.
